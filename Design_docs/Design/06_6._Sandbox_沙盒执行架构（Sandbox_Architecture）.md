## 6. Sandbox 沙盒执行架构（Sandbox Architecture）

Sandbox 是平台的核心执行环境，负责隔离用户代码，保证自动测试、安全执行及环境一致性。

> **当前实现基线（2026-07-27）**
>
> 当前默认执行 adapter 是 `DockerExecutor`，由 API 进程通过 `child_process.spawn('docker', ...)` 启动 digest 固定且受 allowlist 约束的 `node:20-alpine`。composition root 可为开发/测试选择 `LocalExecutor`，生产环境显式拒绝 Local。Sandbox 不是独立 Runner 服务；持久调度与事件归 Submission，当前进程仅拥有正在运行的 child process handle。

### 6.1 Workspace 结构

每个任务都会创建独立 Workspace。
    workspace/
    ├── project/                 # 用户代码
    ├── docs/                    # 学习资料
    ├── tests/                   # 自动测试
    ├── scripts/                 # Build / CI / Lint
    ├── assets/                  # 示例资源
    ├── env_map.json             # 环境配置
    ├── task.yaml                # 任务配置
    └── report/                  # 自动生成报告

Execution Workspace 生命周期结束后自动销毁，避免环境污染；Authoring Workspace 不随执行结束删除。

这里必须区分两种不同生命周期：

- **Authoring Workspace**：PostgreSQL 中的学员草稿、文件和版本，跨请求持久化，不能在一次执行结束后销毁。
- **Execution Workspace**：从 Authoring Workspace 物化到 OS 临时目录的 staging copy，仅供一次容器执行，结束后销毁。

`ExecutionWorkspaceService` 在写入前拒绝绝对路径、盘符、空字节与 `..` 逃逸，解析并校验规范化绝对路径仍位于 staging 根目录内，同时拒绝符号链接/junction 逃逸。path traversal、清理失败与并发隔离由 contract test 覆盖。

> **注：工作区构建演进策略**
> 为控制首个 MVP 的交付范围，当前阶段暂不集成真实的 Git 克隆及复杂脚手架下载能力。
> `pull` 命令仅负责准备最小可执行的 Workspace，通过创建基础目录结构及 `index.js` 等占位文件，满足后续 `child_process` 执行器（Pseudo Sandbox）的运行需求。
> 工作区创建能力通过统一的 `WorkspaceProvider` 抽象进行封装，后续将在相关 Epic 中无缝替换为支持 Git 仓库、模板仓库及脚手架下载等真实实现，而无需修改上层业务流程。这更符合契约稳定、渐进演进的企业级架构实践。

### 6.2 Sandbox 执行流程

1. 下载任务

2. 创建 Workspace

3. 环境检测 (Environment Verification)

> **注：环境检测与依赖安装的演进策略**
> **环境检测**：Docker executor 以固定镜像提供运行时，并在执行前校验任务环境要求与镜像策略；Local executor 仅在开发/测试中检测宿主环境。
> **依赖安装**：MVP 阶段仅对项目级依赖执行自动安装（如检测到 `package.json` 后执行 `npm install`），确保工作区能够完成依赖准备。对于 Node.js、Java、Python、Docker 等宿主运行时，仅执行环境检测并在缺失时返回明确的安装指引，不尝试自动安装。这样能够避免跨平台兼容性、权限控制及系统污染等风险，符合应用层与基础设施层职责分离的原则。

4. 依赖安装 (Dependency Installation)

5. Docker Sandbox (Epic 12)

> **注：执行器渐进式演进策略**
> **Docker MVP 方案**：为了快速验证并保持基础设施稳定，首个 Docker 执行引擎（Epic 12）采用基于 `child_process.spawn` 的 Docker CLI 封装（而不是直接引入厚重的 `dockerode` SDK）。`spawn` 能避免 Shell 注入风险、支持实时日志流，符合长时间任务执行模型。
> **语言支持**：首个版本默认仅提供 `node:20-alpine` 运行时容器，集中精力验证容器生命周期、工作区挂载、超时控制等核心引擎机制。Java、Python 等其他语言支持留待架构稳定后，通过扩展 `RuntimeProvider` 插件形式接入。

6. Build

7. Lint

8. Unit Test

9. Integration Test

10. Collect Report

11. 上传结果

整个流程全部自动完成，无需人工干预。

### 6.3 环境隔离

为了保证不同课程之间互不影响，每个任务运行于独立容器。

Sandbox 提供以下隔离能力：

* 文件系统隔离
* 网络隔离（可配置）
* CPU 限制
* Memory 限制
* 超时终止
* 资源回收

有效避免用户代码影响宿主机环境。

> **注：执行器渐进式演进策略**
> 为控制首个 MVP 的交付范围并降低基础设施复杂度，系统执行能力通过统一的 `Executor` 接口进行抽象封装，避免业务层直接依赖具体实现。
> 当前已经引入 `DockerExecutor` 并作为默认 adapter；`LocalExecutor` 不属于生产执行路径。下一步重点不是再次“引入 Docker”，而是把 adapter 选择、安全策略、runtime profile、日志与取消语义收进深的 Sandbox 模块。
> 该渐进式演进方案能够有效控制项目风险，同时保证后续升级过程中业务层基本无需改动，符合企业级系统的可维护性和架构演进实践。

### 6.4 自动评分机制 (Epic 13)

系统采用多维度评分模型，对学习结果进行综合评价。

评分项包括：

| 指标             | 权重  |
| -------------- | --- |
| 编译通过           | 20% |
| 单元测试           | 30% |
| 集成测试           | 20% |
| Linter 检查      | 10% |
| AI Code Review | 10% |
| 完成时间           | 10% |

> **注：评测体系演进策略**
> **Epic 13 MVP 目标**：不是集成 Jest、ESLint 等具体工具，而是完成**统一评测框架 (Evaluation Pipeline)** 的设计与验证。MVP 阶段定义稳定的 `EvaluationReport` 数据契约及 `ScoreCalculator` 评分机制，支持各维度计分，并打通从执行、评测、评分到前端展示的完整数据链路。
> **测试执行器**：当前 `TestEvaluator` 可基于基础的 `node test.js` 的执行结果生成测试评分，其余评测器（Lint/Compile）采用占位实现或默认满分，以验证评分管道和接口稳定性。待 Epic 20 引入完整任务编辑器及项目模板后，再逐步接入真实工具。

其中，**是否通关仅由自动测试与规则校验决定，AI Review 作为辅助评分项，不影响最终验收结果**，从而保证评分过程客观、可重复、可审计。

### 6.5 可扩展能力

Sandbox 采用插件化设计，可支持不同语言及框架。

当前规划支持：

* Java（Spring Boot）
* Go
* Python
* Node.js
* Rust

未来可通过新增 Runner 插件快速扩展至其他开发语言及企业内部框架，无需修改核心业务逻辑。

### 6.6 当前安全约束与扩展门槛

当前 Docker 参数已包含 `--rm`、内存和 CPU 限制、工作目录与超时终止，但尚未显式配置：

- `--network none` 或可审计的网络策略；
- 非 root 用户、只读根文件系统、capability drop；
- seccomp/AppArmor 配置；
- 镜像 allowlist、digest 固定与供应链校验；
- 每租户并发配额与跨实例取消；
- 执行事件的持久化与重放。

在这些约束落实前，不应把当前 Sandbox 描述为完整企业级隔离。需要横向扩缩容或更强故障隔离时，再把 Sandbox 模块部署为独立 Runner，并以 durable queue adapter 连接 Submission execution 模块。
